# 身份、验证与安全基线

> 状态：已冻结（用户于 2026-08-29 确认）
> 适用项目：P&L Arena / IBKR Founders Season
> 适用对象：产品、设计、前端、后端、运维、审核与客服

## 1. 这份基线解决什么问题

P&L Arena 会处理账户表现、持仓、交易和券商账户等高敏感数据。本基线将以下问题变成可执行的产品与开发规则：

- 在没有注册制度时，哪些排名和勋章是可以做的，哪些不能声称是真实公榜。
- 如何将登录身份、内部用户 ID、公开昵称和券商账户彻底分开。
- 如何区分演示数据、用户自报、文件交叉核对和券商直接来源。
- 如何在不收集原始报表的前提下完成本地 MVP。
- 什么时候才允许引入账号系统、服务端上传、排行榜和 IBKR 直连。
- 遭遇爬虫、越权、密钥泄漏或网站被控制时，如何停损、恢复和通知。

本文档中的“必须”、“禁止”和“不得”都是上线门槛，不是可选建议。

## 2. 已冻结的核心决定

1. 一个自然年等于一个赛季；2026 年是 Founders Season / beta 赛季。
2. 排名的基本单位是“券商账户 × 赛季”（account-season），不宣称“一个自然人只有一个账户”。
3. 用户上传或导入的文件不会因为外观像 IBKR 而成为 `Verified`。
4. 来源等级固定为 `Demo` → `Self-Reported` → `Reconciled Self-Reported` → `Broker-Sourced`。
5. `Self-Reported` 与 `Broker-Sourced` 必须分榜。不得只用一个小图标混在同一个默认榜单中。
6. MVP 仍不设登录、后端、数据库或真实公开排行榜；只能展示本机身份、本地勋章和 Arena Demo。
7. CSV 是 MVP 的主要机器输入；PDF 只是可选的交叉核对材料。PDF-only 不得进入正式排名。
8. 原始 CSV/PDF 以及完整解析结果默认只在用户浏览器的当次会话内存中处理，不上传服务器，不做默认长期保存。
9. 排行榜的绝对 P&L 榜与 TWR/相对回报榜必须分开。资本组别可用余额区间，精确 NAV 默认私密。
10. 在 `Self-Reported` 与 `Reconciled Self-Reported` 等级不举办有实际价值奖品的比赛。
11. 不开发“AI 假报表检测器”。文件仅能通过结构、算术、跨文件一致性和直接来源逐级增加可信度。
12. 永不收集 IBKR 用户名、密码、2FA 验证码、交易权限或可下单凭据。

## 3. 新的本地存储决定（替代旧默认）

### 3.1 旧方案即日失效

`PROJECT_DECISIONS.md` 和 `README.md` 中原有的“将最新的完整标准化报表默认保存到 `localStorage`”方案，已被本轮用户决定取代。

新默认是：

- 原始文件、原始行、持仓、交易、金额、账户标识和完整标准化报表只存在于当次浏览器会话内存。
- 页面刷新、关闭标签或用户点击“清除”后，敏感报表数据不应仍可恢复。
- `localStorage` 只允许保存非敏感偏好，例如界面语言、主题、已阅说明和本地随机 ID。
- 任何“记住本地报表”功能都必须是将来单独评审、明确选择开启的功能，不得恢复为默认。
- 未来即使允许本地记忆，也应优先保存经审批的最小汇总结果，而不是原始行和完整报表。

### 3.2 开发验收标准

- [ ] 代码中不存在将完整 normalized report 写入 `localStorage`、`sessionStorage`、IndexedDB 或 Cache Storage 的路径。
- [ ] 导入真实报表后检查以上存储区，不得找到账户、金额、标的、交易或原始行。
- [ ] 刷新页面后不得自动恢复完整报表。
- [ ] 用户点击“清除”后，内存引用、文件对象 URL、页面展示和可下载结果均失效。
- [ ] 分享卡不包含账户号、姓名、原文件名、精确 NAV 或未经用户确认的持仓。

## 4. 身份模型：一个人在系统中不是一个“昵称”

### 4.1 必须分离的标识

| 对象 | 作用 | 公开性 | 规则 |
| --- | --- | --- | --- |
| `user_id` | 系统内勋章、排名、申诉和封禁的稳定归属 | 永不公开 | 服务端生成随机不可猜 ID；不用邮箱或昵称充当 |
| `login_identity` | 登录与找回 | 不公开 | 邮箱魔法链接、通行密钥，以及未来可选 Apple/Google |
| `public_nickname` | 榜单、卡片和社区展示 | 用户主动公开 | 允许修改；不是主键；需要重名和冒充策略 |
| `broker_account_pseudonym` | 识别同一券商账户是否在同一赛季重复参赛 | 永不公开 | 服务端密钥 HMAC；禁止明文或普通无密钥哈希 |
| `season_entry_id` | 某一账户在某一赛季的一个席位 | 可对外使用独立不可猜 ID | 包含赛季、来源等级、计算版本和更新时间 |
| `award_record` | 勋章的授予、撤销和解释 | 按用户隐私选项公开 | 服务端授予；保留规则版本、证据等级和撤销原因 |

券商账户号是低熵标识，只用 SHA-256 等普通哈希仍可能被枚举。跨设备连续性仅在有服务端时使用秘密密钥的 HMAC 构建，密钥不进入浏览器、日志或代码仓库。

### 4.2 无注册 MVP 的边界

无注册阶段可以：

- 在浏览器本地生成随机 ID；
- 让用户填写本地昵称；
- 根据当次报表触发 Local Achievement；
- 生成由用户主动下载或分享的卡片；
- 显示明确标注为 Demo 的 Arena。

无注册阶段不能声称：

- 昵称归属已验证；
- 换设备后一定能找回成绩；
- 已阻止一人多账号或多个昵称；
- 勋章永久归属某个自然人；
- 排名是真实、公平、可申诉的公开排行榜。

### 4.3 身份演进顺序

| 阶段 | 能力 | 允许的声称 | 进入下一阶段的门槛 |
| --- | --- | --- | --- |
| 0. 本地 MVP | 本地 ID、昵称、本地勋章、Demo | Local / Demo | 本地数据边界、真实报表对账和静态站安全通过 |
| 1. 封闭测试 | 邀请码＋邮箱魔法链接或通行密钥 | 可找回的测试身份 | 托管身份、越权测试、审计日志和删除流程通过 |
| 2. 公开账号 | 稳定 `user_id`、公开昵称、隐私设置 | Self-Reported 或 Reconciled 账户赛季档案 | 稳定授权、限速、申诉/封禁、监控和恢复演练通过 |
| 3. 券商来源 | 获批的 IBKR 只读数据连接 | Broker-Sourced | IBKR 审批、密钥托管、撤销/轮换、独立安全评审通过 |
| 4. 有奖竞赛 | 可能需要实名、KYC、地区和竞赛合规 | 符合当届规则的正式竞赛 | 法律、税务、券商和奖品合规审查完成 |

## 5. 排名与勋章基线

### 5.1 排名对象和更新规则

- 一条正式成绩必须绑定 `season_entry_id`，不得只绑定昵称。
- 一个 account-season 在某一来源等级下只有一个当前快照。
- 新的 YTD 快照替换旧快照；绝不将两份重叠的 YTD 报表相加。
- 服务端排名阶段必须由服务端从允许的最小汇总数据重新计算；不接受客户端直接声称“我是第几名”或“我已获勋章”。
- 每条成绩必须记录赛季、报表期间、来源等级、计算规则版本、币种和最后更新时间。
- 规则版本发生会改变结果的变化时，必须重算并显示版本，不得静默改分。

### 5.2 榜单必须分开

- `Season P&L` 榜：绝对金额，受资金规模影响。
- `Season Return / TWR` 榜：相对回报，必须先冻结 IBKR 字段、币种与缺失值规则。
- `Capital Division` 仅使用资产区间，不将精确 NAV 公开，也不把组别当成投资技能评分。
- `Self-Reported`/`Reconciled Self-Reported` 与 `Broker-Sourced` 必须有分离的默认入口、标题和筛选状态。

### 5.3 勋章规则

- 本地 MVP 的勋章必须标注 `Local Achievement` 或等价文案，不称“官方认证”。
- 正式勋章必须保存触发规则版本和授予时的来源等级。
- 来源等级降级、结果重算或账户违规时，勋章可撤销；撤销需要原因、时间和操作人记录。
- 客户端仅展示勋章，不是正式勋章的最终授予方。

### 5.4 排名验收标准

- [ ] 使用两个相同昵称创建测试数据时，两个用户的成绩、勋章和权限仍完全分离。
- [ ] 修改昵称后，成绩与勋章不丢失、不转移。
- [ ] 上传新 YTD 快照只替换同一 account-season 的旧快照，排名不相加。
- [ ] 绝对 P&L、TWR、资本组别与来源等级均在界面中分开标注。
- [ ] 对客户端篡改“分数”、“勋章”、`user_id` 或来源等级的请求，服务端拒绝并记录审计事件。
- [ ] 未登录或被封禁用户无法创建、更新或删除他人的 season entry。

## 6. 报表来源和验证等级

| 等级 | 数据来源 | 已证明 | 未证明 | 是否允许正式 Broker-Sourced 榜 |
| --- | --- | --- | --- | --- |
| `Demo` | 产品自带的合成示例 | 产品功能和规则展示 | 任何真实用户成绩 | 否 |
| `Self-Reported` | 用户本地选择的 CSV | 文件可解析并通过基本结构检查 | 文件是否由 IBKR 原始签发 | 否 |
| `Reconciled Self-Reported` | 同期 CSV＋PDF | 账户、期间、金额、工具和会计关系交叉一致 | 两份文件是否被同步篡改 | 否 |
| `Broker-Sourced` | 经用户授权、经 IBKR 允许的只读连接 | 平台按受控来源直接取得快照 | 仍需要处理账户归属、竞赛规则和欺诈异常 | 是 |

### 6.1 `Reconciled Self-Reported` 的必要检查

1. 文件类型、文件头、大小、页数、行数、加密/附件/交互结构。
2. Activity Statement 类型、自然年 YTD 期间、单一账户、基础币种和生成时间。
3. NAV bridge、MTM 组成项、Realized/Unrealized、Cash Report、Trades 小计、Open Positions、入出金、费用、分红、税和利息的算术闭合。
4. CSV 与 PDF 的期间、账户、币种、关键汇总和工具清单交叉一致。
5. 所有差异必须显示。超出冻结容差时拒绝升级，不得自动舍弃异常行。

文件哈希只证明“平台收到后没有改变”，不证明“文件最初由 IBKR 产生”。PDF 没有有效券商数字签名时，不比 CSV 更真实。

### 6.2 来源等级验收标准

- [ ] 界面在成绩、勋章、分享卡和榜单每个重要位置展示来源等级。
- [ ] 上传 CSV 后的状态最高只能是 `Self-Reported`。
- [ ] CSV＋PDF 全部检查通过后的状态最高只能是 `Reconciled Self-Reported`。
- [ ] 修改客户端变量、URL 参数或本地存储无法将状态升为 `Broker-Sourced`。
- [ ] `Broker-Sourced` 只能由服务端从获批的直接来源产生，并记录来源、查询版本、取得时间和完整性摘要。
- [ ] 任何核对失败都导致可理解的警告或拒绝，而不是静默猜测。

## 7. 数据收集和隐私白名单

数据收集采用“默认不收，逐字段批准”。“以后可能用来分析”不是充分理由。

### 7.1 产品遥测允许项

在有明确告知、适用时取得同意、设定保留期的前提下，只允许：

- 应用版本；
- 界面语言；
- 导入成功/失败；
- 标准化错误代码（不包原始错误文本）；
- 报表区块存在与否的位图（不包区块内容）；
- 文件大小、行数、页数和解析耗时的区间，不上传精确值；
- 浏览器大类和设备大类，不做跨站指纹；
- 用户是否完成主要流程的布尔值。

遥测事件必须有固定 schema 和字段白名单，不允许“额外属性”、任意 JSON、请求体、DOM 快照或屏幕录制。

### 7.2 服务端排名阶段允许的最小数据

- 内部 `user_id`、登录提供方内部标识、公开昵称；
- 隐私同意版本、时间和撤回状态；
- 赛季、来源等级、计算版本、分数、股票/期权/其他汇总、更新时间和是否公开；
- 资本组别，不是精确 NAV；
- 用服务端秘密密钥生成的券商账户伪名。

### 7.3 安全日志允许项

- 登录失败、会话撤销、被拒绝的越权操作；
- 文件拒绝的标准化原因代码；
- 管理员、权限、部署、密钥轮换和数据删除变更；
- 限速、挑战、防火墙与异常成本告警。

安全日志不得记录原始文件、文件名、账户号、姓名、地址、标的、持仓、金额、原始交易时间、请求体、会话 Cookie、令牌、密钥、密码或 2FA 信息。

### 7.4 研究数据与排名数据分开

如果未来需要使用真实交易数据训练解析器或研究新功能，必须：

- 提供与“参加排名”分开的自愿同意；
- 告知用途、字段、访问人、保留期和删除方法；
- 将原始研究集与生产排名库隔离；
- 去除直接身份标识，并单独评估重识别风险；
- 到期删除并保留不包含敏感内容的删除记录。

## 8. 分阶段安全门槛

### A. 当前本地/静态 MVP

必须：

- 无后端、无数据库、无原始文件上传；
- 原始文件与完整解析结果默认只在内存；
- 导入页不加载第三方广告、聊天工具、会话回放、远程字体或未批准的分析脚本；
- 静态资源和字体自托管，依赖最小化并锁定；
- 对 CSV/PDF 所有文本做不可信输入处理，禁止使用 `innerHTML` 渲染报表内容；
- 对文件大小、行数、页数、字段长度、解析时间和内存用量设置上限；
- 大文件解析放在 Web Worker 或等价隔离边界，防止卡死主界面；
- 配置严格 CSP，不允许任意内联脚本或未批准网络目的地；
- 对导出卡片和报错路径做敏感字段泄漏检查。

验收：

- [ ] 使用真实样本执行导入时，浏览器网络面板中没有原文件、解析行、账户、标的或金额外发。
- [ ] 无网络时导入、计算、勋章和卡片仍可完成。
- [ ] 对过大、过长、恶意公式、超时和畸形文件的测试会安全拒绝，且页面不卡死。
- [ ] CSP 在预发布环境生效，未批准脚本和网络连接被拒绝。
- [ ] 日志、错误页、分享卡和本地存储通过敏感值检索。

### B. 公开静态 Beta

除 A 阶段外，必须：

- 使用受管的边缘托管平台，不在创始人个人 Mac 或临时 VPS 上运行生产站；
- GitHub、托管平台、域名注册商和主邮箱全部启用通行密钥或双重验证；
- 日常管理账号与紧急 Owner 账号分开，无共享账号；
- 主分支保护、必需复核、生产部署审批、可回滚不可变部署；
- 依赖锁定、漏洞检查、密钥扫描，禁止将生产密钥进入前端包；
- 启用托管平台的 DDoS 缓解和防火墙能力，为异常请求和成本设置告警；
- 定义紧急挑战、限流、回滚和暂停功能的操作者。

说明：公开网页无法保证不被爬取，`robots.txt` 不是安全控制。敏感数据必须根本不出现在公开 HTML、JavaScript bundle、source map 或无需登录的 API 中。WAF 不能修复代码越权和登录缺陷。

验收：

- [ ] 通过实际帐号检查确认以上所有管理面启用 2FA/通行密钥。
- [ ] 未经审批无法从主分支发布生产环境。
- [ ] 演练一次回滚、紧急暂停和费用告警，不只查看开关是否存在。
- [ ] 生产构建不包含密钥、原始样本、真实账户数据或未禁用的公开 source map。

### C. 账号、勋章与排行榜

除 A、B 阶段外，必须：

- 使用成熟的托管身份服务，不自建密码存储；
- 优先邮箱魔法链接或通行密钥；
- Web 会话使用 Secure、HttpOnly、适当 SameSite 的 Cookie，不将长期登录 token 放在 `localStorage`；
- 服务端对每个对象执行授权检查，不因客户端隐藏按钮就认为有权限；
- 对登录、昵称变更、成绩更新、卡片生成和榜单查询做分层限速；
- 账号删除、数据导出、会话撤销、申诉和封禁有明确流程；
- 生产数据不复制到开发环境，管理员访问最小权限且可审计；
- 备份加密，并实际完成恢复演练。

验收：

- [ ] 测试用户 A 无法读取、修改、删除或枚举用户 B 的私密资料和 season entry。
- [ ] 登录 token 不出现在 URL、前端日志、分析事件或浏览器长期存储。
- [ ] 授权、限速、CSRF/XSS、账号枚举、会话撤销和管理员操作有自动测试或专项验证记录。
- [ ] 用户删除账号后，活跃数据按规则删除，备份按公开保留周期自然过期。
- [ ] 从加密备份恢复到隔离环境的演练实际成功。

### D. 服务端原始报表上传（默认不开启）

只有当本地处理无法完成已验证的产品需求，且用户单独批准后，才可提案开启。除 A、B、C 阶段外，必须：

- 原始文件放入私有隔离存储，随机服务端文件名，永不使用公开 URL；
- 扩展名、MIME、文件签名和内部结构多重校验，只允许已批准的报表格式；
- 大小、页数、行数、压缩比、并发、CPU、内存和处理时间上限；
- 在无网络出口、最小权限的隔离处理器中解析，并进行恶意软件/活动内容检查；
- 不处理业务不需要的 PDF JavaScript、附件、表单、外部链接或密码保护文件；
- 静态加密、传输加密、最小访问、访问审计、短保留期和用户删除通道；
- 不在错误跟踪、工单、备份或开发环境中无限期复制原始文件；
- 上线前完成文件上传、解析器逃逸、越权、公开 URL、删除和备份的独立安全测试。

验收：

- [ ] 上传任意扩展名伪装、超大文件、压缩炸弹、带脚本 PDF、加密 PDF 和恶意公式文件都被安全拒绝。
- [ ] 一个用户无法通过改 ID、URL 或文件名访问他人原文件。
- [ ] 用户删除请求完成后，主存储不再可访问，备份中的副本按明示期限过期。
- [ ] 开发者不能为了调试随意下载生产原始报表。
- [ ] 独立测试中的严重和高危问题全部修复后才能开启功能。

### E. IBKR 直接来源和 token

只有在 IBKR 对该产品和连接方式明确允许后才进入本阶段。必须：

- 永不索取或存储 IBKR 用户名、密码、2FA 验证码、交易权限或可下单凭据；
- 权限限定为产品确实需要的只读报表范围；
- token 只在服务端保存，使用托管密钥库/KMS 或等价密钥管理，不进入前端、URL、代码仓库、日志或支持工单；
- 使用可用的 token 有效期、受限来源 IP、最小查询和频率限制；
- 建立用户断开授权、token 撤销、轮换、过期、异常调用告警和事故泄漏响应；
- `Broker-Sourced` 快照保留查询配置版本、取得时间、来源类型、计算版本和完整性摘要，但不公开 token 或券商账户号；
- 在处理首个真实用户 token 前，完成独立渗透测试和密钥/权限架构评审。

验收：

- [ ] 书面记录并核对 IBKR 对当前 API/Flex 用法的批准、法律条款、产品用途和数据范围。
- [ ] 测试 token 只能读取允许的报表数据，无交易能力。
- [ ] 前端 bundle、网络响应、日志、追踪、报警和备份中均无明文 token。
- [ ] 用户点击断开后，平台无法继续取数，且撤销事件可审计。
- [ ] 演练 token 泄漏：在预定时间内完成撤销、转移或重新生成、会话失效、影响调查与用户通知决策。
- [ ] 独立渗透测试无未修复的严重或高危问题。

## 9. 威胁模型与常设控制

| 风险 | 现实边界 | 最小控制 |
| --- | --- | --- |
| 公开页爬虫 | 无法保证不被爬 | 只公开用户主动公布的昵称和汇总成绩；私密数据不进公开页面/API；对高成本路由限速和挑战 |
| 恶意文件导致页面卡死或执行代码 | CSV/PDF 内容都是不可信输入 | 类型/结构验证、限额、超时、隔离解析、纯文本渲染、CSP |
| 攻击者修改客户端分数 | 前端代码和本地数据可被用户自己修改 | 本地阶段只声称 Self-Reported；正式榜单服务端重算与授予 |
| 用户 A 读取用户 B 数据 | 登录不等于授权 | 每个服务端对象做所有权检查；不信任客户端传入的 `user_id` |
| 管理员/主邮箱/域名被控制 | 这会直接导致网站被篡改 | 通行密钥/2FA、独立 Owner、最小权限、审计告警、部署审批、可回滚构建 |
| 前端依赖或第三方脚本窃取报表 | 浏览器中的第三方代码可读取同页数据 | 导入页禁止第三方脚本，自托管资源，依赖锁定/审查，严格 CSP |
| token/密钥泄漏 | 密钥一旦进入前端或日志就难以收回 | 服务端密钥管理、最小权限、自动扫描、轮换/撤销、异常告警 |
| 攻击或爬虫制造巨额成本 | 未被阻断的有效请求仍可产生费用 | 预算告警、限速、缓存、挑战、请求限额、紧急降级/暂停 |

## 10. 事件响应基线

网站被篡改、密钥疑似泄漏、发现越权、异常原文件访问或大规模爬虫时，不在未知影响下继续对外运行。

### 10.1 处置顺序

1. **确认和分级**：记录发现时间、报警来源、受影响功能和当前证据；不急于删日志。
2. **立即止损**：按风险暂停上传、写入、榜单更新或整站；开启挑战/限流；回滚到已知安全版本。
3. **撤销凭据**：撤销可疑会话、API token、部署密钥和管理员凭据；立即更换受影响密钥。
4. **保全证据**：保留审计日志、部署版本、时间线和配置快照；避免把原始金融数据扩散到事故群聊。
5. **调查影响**：确定从何时开始、攻击者能做什么、哪些用户/字段/地区可能受影响。
6. **升级协调**：按需联系托管平台、IBKR、独立安全专家、律师和保险方。
7. **通知**：根据实际影响和适用法律决定用户、合作方和监管通知；不猜测、不隐瞒已确认事实。
8. **安全恢复**：修复根因，重置凭据，重新部署，进行回归检查和受控恢复。
9. **复盘**：记录时间线、根因、影响、止损效果、待办责任人和截止日期，把经验加入测试与门槛。

### 10.2 必须预先准备的“紧急卡”

上线前在安全的离线位置保存一页简明操作卡，内容至少包含：

- 如何暂停上传、写入和整站；
- 如何回滚上一个稳定版本；
- 如何撤销会话、部署密钥和 IBKR token；
- GitHub、托管平台、域名、邮箱、IBKR、安全和法律联系方式；
- 谁有权决定停站、恢复和对外通知；
- 日志和证据在哪里，如何避免覆盖。

每次进入新安全阶段前至少演练一次，不得仅凭文档存在就判定已具备响应能力。

## 11. 开发与发布的通用验收清单

每一次涉及身份、文件、排名、勋章、遥测、日志、存储或券商连接的发布，必须回答：

1. **收集了什么？** 字段白名单、用途、保留期、用户删除方法已记录。
2. **数据去了哪里？** 网络目的地、存储、日志、备份和第三方均已枚举。
3. **谁能访问？** 用户、管理员、开发者和服务帐号的最小权限已测试。
4. **能否被客户端伪造？** 排名、勋章和来源等级的最终判定位置已确认。
5. **如何失败？** 超限、畸形、缺字段、对账差异和依赖失效时有可见警告，不静默忽略。
6. **怎样停止？** 紧急暂停、回滚、撤销密钥与用户断开方式已演练。
7. **怎样恢复？** 备份恢复或静态重部署已实际通过。
8. **宣称是否过度？** `Demo`、`Self-Reported`、`Reconciled Self-Reported` 和 `Broker-Sourced` 文案与真实证据一致。

如果任一答案不清楚，该功能不进入下一安全阶段。
