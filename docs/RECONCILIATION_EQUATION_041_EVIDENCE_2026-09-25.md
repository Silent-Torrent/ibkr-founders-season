# Checkpoint 0.41 — 三项财务核对展开式与精度

## 为什么改

0.40 已让解析器保留三项真实的有符号差额，但账本页面只在概览显示“全部资产盯市”差额。期间盈亏和净资产衔接的差额，以及三项的报表值、计算值，都只能在内部数据里看到；展开“核对检查”时只有状态、帮助文字和来源位置。对不熟悉财务数据的用户，这不足以解释一个“符合容差”的结果从何而来。

现在每项已有的原生展开区，在三个金额均有证据时用语义化的三行清单显示“报表值／计算值／有符号差额”。数字仍按“报表值减计算值”确定正负；缺少金额的 `NOT_AVAILABLE` 等状态不补零、不伪造等式。原有的来源区块、行号、字段继续保留。纯虚构 Demo 的缺失两项也不会出现编造的数字。只改变本地展示，不改变 Season P&L、容差、警告、排名资格或券商认证状态；导入数据仍标为 `Self-reported · not broker-verified`。

一般的组合金额显示会四舍五入，不适合放在核对等式里：例如 `740.123457` 与 `740.123456` 不应都显示成 `$740`。新增的核对数值格式会保留归一化后 JavaScript 数值的可回读十进制精度；如果普通货币格式需要超过 20 位小数，改用足够有效数字的科学计数法，避免不同的已接受数值显示成同一金额。有符号差额也采用相同的精度边界，保留旧有普通小额货币至少两位小数的显示规则，包括日元的既有合同。原始 CSV token 的尾随零本来就不保留，这里不声称重建原始 token 写法。

容差说明、核对帮助、三行等式与来源行在窄屏下均至少 12px；原有样式的来源字段曾是 8px、技术表头 7px。字体调整不改变来源内容。

## 验证与反例

- 三语静态渲染先在旧页面因缺少三行等式失败；旧生产版 Chrome 经真实 Worker 导入全虚构 `+0.000001` MTM CSV 后，新增断言实测三项的等式行数为 0，构成展示缺口的反例。
- 新版三语静态检查：每项有完整数值时均显示三行语义 `<dl>/<dt>/<dd>`；英语、简体、繁体标签和正负差额均存在，Demo 的两项缺失数值不被编造。
- 生产版 Chrome 经真实 Worker 导入同一完全虚构 CSV：MTM 报表值含 `740.123457`，计算值含 `740.123456`，差额 `+$0.000001`；期间盈亏显示 `-$0.000001`，NAV 差额为零。模拟 320px 视口中，三项原生 `<summary>` 经完整 CDP Enter 键序列实际展开，等式和来源行有非零可见尺寸；容差说明、帮助、金额和来源字段均至少 12px、无横向裁切。初版测试器仅发 keyDown/keyUp 没有字符事件而失败；补完整键序列后通过，不能把这一测试器问题误记为产品键盘故障。此结果是桌面 Chrome，不是 iPhone Safari/VoiceOver 实听。
- 高精度独立红测确认解析器接受两个相邻但不同、需超过 20 位小数的全虚构数值时，旧新加的金额格式器会把它们显示成同一个数；修订后金额和正负差额都保留可回读值及符号，既有 `JPY +¥0.40` 显示也继续通过。
- 最终 Node 22 `npm run check`、单独 `npm run build`、`git diff --check` 退出 0；生产 Chrome 完整套件记录 58 次本地请求、36 个 Worker target；高危依赖审计为 0 个漏洞。本次产物 `index-gS9zFKav.js`、`ibkrParser.worker-DH4j2t4Z.js`、`index-C91NXhFt.css`。
