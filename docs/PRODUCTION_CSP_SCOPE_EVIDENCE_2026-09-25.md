# Production CSP connection scope — 2026-09-25

Status: **VERIFIED LOCAL**, not deployment approval or a closed release gate.

## Problem and bounded change

The source `index.html` previously declared `connect-src 'self' ws:` in a CSP meta tag. The `ws:` scheme expression is not limited to the page's host and also matches `wss:` under CSP's secure-upgrade matching rule. This left a built page served without a separate host CSP header able to initiate a cross-origin WebSocket if future or injected code attempted one. It is a policy gap, **not** evidence that the current app opened such a connection or sent a statement anywhere. The existing Vercel configuration already specifies `connect-src 'self'` in an HTTP response header. When both policies are delivered, the browser enforces both, so that header restricts the broader meta policy on that host. Vercel currently has no surviving deployment, and the project's L deployment freeze remains in force.

The production HTML source now says `connect-src 'self'`, restricting destinations under CSP's `'self'` matching rule rather than promising a literal same-origin-only rule in every scheme-upgrade case. A small Vite plugin applies only while serving the development page and restores `ws:` in its transformed HTML for HMR. It checks that exactly one expected CSP fragment exists before replacing it, so an HTML policy change cannot silently skip the dev exception. The production build does not receive the exception; `vite preview` serves the built HTML unchanged. `vercel.json` retains its existing `connect-src 'self'` header. No product parsing, accounting, storage, dependency, hosting or private-statement data was changed for this fix.

This split follows [Vite's HTML transform and conditional plugin API](https://vite.dev/guide/api-plugin) and its [development WebSocket configuration](https://vite.dev/config/server-options). The [W3C CSP specification](https://www.w3.org/TR/CSP/) defines `connect-src`, scheme matching and the cumulative effect of multiple policies. Browser implementations have differed on whether `connect-src 'self'` permits a same-origin WebSocket, so retaining explicit `ws:` for development avoids relying on that behavior for HMR. This is a development exception only, not an application network requirement.

The probe runs after the ordinary no-error and no-WebSocket assertions so its expected violation does not obscure the product's ordinary network gate. ## Boundary that remains for hosting

The meta policy constrains the document, but the IBKR parser runs in a separate same-origin module Worker. A Worker loaded from a normal HTTP URL generally takes its own CSP from the **Worker script response header**, rather than inheriting the document's meta policy; see the [HTML Standard's Worker policy-container algorithm](https://html.spec.whatwg.org/multipage/browsers.html). The Vercel rule is configured for all paths, including the built Worker asset, but a different static host must explicitly deliver and verify a suitable CSP header on that asset. `connect-src 'self'` also still permits same-origin connection APIs; the no-upload promise additionally rests on the functional-source policy gate and observed production browser network behavior. Protected-host response headers, Worker MIME/CSP, Network and Storage remain deployment-specific release checks under the existing freeze.
