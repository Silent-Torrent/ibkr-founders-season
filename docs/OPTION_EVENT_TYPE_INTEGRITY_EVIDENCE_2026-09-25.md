# Option-event type integrity — 2026-09-25, checkpoint 0.29

Status: `VERIFIED_LOCAL`, not release approval. This records a bounded local parser and accessibility-tree change, not a real-device, broker-authenticity or deployed-site acceptance.

## Reproduced problem and narrow repair

Only the repository-owned, fully fictional current-schema fixture was used. Replacing one option Trades row's `Code=A` with `A;Ep` previously produced `errors=[]`, `dataQuality=good` and one Assignment: the parser chose its first recognizable lifecycle type even though the same row also said expiration. A first repair blocked that combination, but independent in-memory checks then reproduced `Cancelled Assignment` as a good Assignment and `Exercise Reversal` as a good Exercise. These are invented test strings, not claims about an IBKR export. The distinction matters because accepting either as a completed positive event would misstate the displayed count.

The parser now recognizes only the bounded positive tokens `A`/`Assignment`/`Assigned`, `Ex`/`Exercise`/`Exercised`, and `Ep`/`Expiration`/`Expired`, with `P` permitted as a non-event partial-execution modifier. Repeated tokens of one type, such as `A;A`, retain one event. A row with conflicting lifecycle types, unsupported lifecycle-like codes, cancellation/reversal wording, non-ASCII characters or an ambiguous type is rejected with `option_event_type_conflict`; it is not guessed into an event or used to replace an open report. A lifecycle row with a missing option contract or a contradictory option/stock classification also follows an existing blocking accounting/alias diagnostic. This is a cautious parser contract for supported shapes, not a report-authenticity check or proof of all broker code combinations.

The fictional regression set covers positive `A;P`, `A;A` and `Assignment;A`; conflicting `A;Ep`, `A;Ex`, `Ex;Ep`, `Assignment;Expired`, punctuation and Unicode variants; negated or reversed wording; missing contract and mislabeled asset category. The dedicated lifecycle section retains count precedence over Trades to avoid double-counting trade and settlement rows. A separate cross-section assertion now checks that a contradictory lifecycle code in the otherwise unused Trades fallback still blocks the report; it does not combine the two sources' event counts. Before that cross-check was added, an in-memory fictional fixture with a valid dedicated section and `A;Ep` in Trades returned `good` without a diagnostic. That result is historical red evidence, not the intended final behavior.

## Official-code compatibility boundary

The [IBKR Reporting Guide code table](https://www.ibkrguides.com/reportingreference/reportguide/codes_realized.htm) defines `AEx` as an automatic exercise related to a dividend recommendation, `MEx` as a manual exercise related to a dividend recommendation, and `GEA` as expiration **or** assignment from offsetting positions. It also defines `Ca` as cancelled, `Co` as corrected and `P` as partial execution. This source describes codes used across statement sections; it does not, by itself, prove the exact row shape in our supported English Activity Statement CSV.

In an earlier in-memory Trades test, `MEx` and `GEA` silently disappeared while the report remained `good`; `AEx` was already rejected. The current bounded rule treats all three as unsupported/ambiguous lifecycle-like codes and fails closed instead of silently omitting or assuming an event type. It does **not** count `AEx` or `MEx` as verified Exercise, and it cannot disambiguate `GEA`. F01 remains `OPEN` until a source-backed real Exercise CSV/Flex row establishes section, header, row shape, date, contract, underlying, provenance and no duplicate P&L, followed by a separate fictional regression. A synthetic `Ex` substitution or this official code glossary cannot close F01.
