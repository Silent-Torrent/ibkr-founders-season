# Checkpoint 0.37 — unverified BOA/EOA account boundaries (2026-09-25)

## Boundary and evidence

This checkpoint uses only the repository's wholly fictional current-schema statement and derived CSVs. No personal IBKR report, phone file, external host or deployment was used. The [official IBKR Activity Flex delivery guide](https://www.ibkrguides.com/reportingreference/reportguide/delivery%20configuration%20and%20general%20configuration.htm) names `BOA` and `EOA` as begin/end account record descriptors but does not give their CSV payload layout on that page. Consequently the rule below is a conservative **MVP compatibility policy**, not a claimed official field specification, account authentication or a finding that a rejected file is forged.

Before the repair, a wholly fictional `MTMP,BOA,Stocks,ZZFICTA,999999` row in a recognized performance section produced `errors=[]`, a `good` report and the unchanged Season P&L because the first-pass index returned immediately for `BOA`/`EOA`. The new parser assertion failed against that behavior. A separate read-only probe found the same blind spot in the Financial Instrument Information mapping path. Independent review identified a deeper boundary: even empty `BOA`/`EOA` markers denote begin/end account, and the current single-account parser cannot establish their pairing or account attribution.

The first-pass index now flags **any** `BOA` or `EOA` marker in either of the first two CSV cells, with or without payload, across sections before materialization or instrument mapping. For an otherwise in-bounds statement it emits the existing `accounting_section_conflict` diagnostic and no report; an independent earlier capacity or row-count failure can take precedence. Parser regressions cover both descriptors in supported accounting sections, Financial Instrument Information and an otherwise unmaterialized section, including empty markers, blank trailing CSV cells and first-cell forms. Other supported rows still retain the existing harmless-blank-tail policy. This **does not** establish a BOA/EOA field count or identity mapping; a genuine Flex export that uses these account-boundary records is now unsupported until an authoritative layout or consented structural sample permits a validated pairing/identity rule. The rejection is not proof that the export is forged.

It imports each through the built parser Worker, checks the visible error, accessibility alert and recovery instruction, then verifies that the previously accepted fictional Ledger row count, data-source badge, Season P&L and table text are unchanged. This is a desktop browser test using controlled file-input selection, not an iPhone native picker or a VoiceOver speech result.
